# too-voice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `too-voice` skill that polishes or composes English so it reads as the writer's own message, learning the voice on the fly from their GitHub comments and pasted Slack threads.

**Architecture:** One `SKILL.md`, no scripts. Each run fetches the writer's public GitHub comments with one `gh` call, filters them with `jq`, optionally adds the writer's lines from a pasted Slack thread, and writes using those samples plus generic non-native rules. Nothing is stored.

**Tech Stack:** Claude Code skill (markdown), `gh` CLI (GraphQL), `jq` (bundled in `gh --jq`).

**Spec:** `docs/superpowers/specs/2026-11-13-too-voice-design.md`

## Global Constraints

- Public repo: nothing committed may describe the writer's voice or contain their messages. Test fixtures and test outputs live in the session scratchpad, never in the repo.
- No setup beyond `make install` (`claude-skills-local` symlinks the skill) and `gh auth login`.
- No stored profile, no extra folders, no MCP connectors.
- Never commit without the user's explicit approval (`~/.claude/CLAUDE.md`).
- Format touched markdown with `npx prettier --config config/prettier/.prettierrc`.

## Review Focus

- A pasted Slack thread where the writer quotes another participant inline: the quote must not count as the writer's sample (Task 3, Step 3).
- A draft with a harmless non-native phrase next to a real typo: only the typo changes (Task 3, Step 2).
- `gh` logged out: one warning line, then output from the generic rules, no crash or retry loop (Task 3, Step 4).
- A thread with no line from the writer's `git config user.name`: the skill asks which lines are theirs instead of guessing (Task 3, Step 3).
- Compose from Italian intent for Slack: the output stays short and informal, without native idioms ("circle back", "touch base") (Task 3, Step 5).

`````markdown
# Write in my voice

Make English read as the writer's own message: their vocabulary level,
phrasing and tone. The goal is a message nobody would flag as AI-written or
as written by someone else.

## Learn the voice

Do this on every run. Keep samples and observations in context only; never
write them to a file.

1. Fetch the writer's recent public GitHub comments:

   ````sh
   gh api graphql -f query='{viewer{issueComments(last:100){nodes{body repository{isPrivate}}}}}' --jq '.data.viewer.issueComments.nodes[] | select(.repository.isPrivate | not) | .body | select(test("🤖") | not) | select(test("^\\s*@(dependabot|copilot)\\b") | not) | gsub("```[\\s\\S]*?```"; "") | split("\n") | map(select(test("^\\s*>") | not)) | join("\n") | gsub("^\\s+|\\s+$"; "") | select(length > 0)'
   ````

   `🤖` marks AI-drafted comments, and `@dependabot`/`@copilot` lines are
   bot commands. Neither is the writer's voice.

2. If the user pasted a Slack thread, keep only the writer's lines:
   - The writer is `git config user.name`, matched against sender headers
     (`Name  [10:05 AM]`). If no header matches, ask which lines are theirs.
   - A bare timestamp (`[10:06 AM]`) continues the previous sender.
   - Strip `(edited)`, URLs and link-preview text.
   - Drop any text that repeats another participant's message: it's a quote.
   - Other participants' lines are context, never style samples.

3. Note sentence length, formality, recurring phrases, openers and closers,
   emoji, and which native idioms the writer never uses.

4. If `gh` fails or fewer than 5 samples remain, say so in one line and
   continue with the rules below only.

## Modes

- **Polish** (default, when the user gives a draft): fix only errors that
  hurt clarity. Keep the writer's words, order and structure. If a calque
  may confuse a native reader, keep it and suggest an alternative instead
  of replacing it. Return the text, then a short list of changes and
  suggestions.
- **Compose** (when the user gives an intent, in Italian or English): write
  the message in the writer's voice for the channel they name. Ask for the
  channel only if it's unclear.

## Rules

- Never raise vocabulary above the writer's level. Add no native idiom
  ("circle back", "touch base", "ballpark") the samples don't show.
- Keep non-native phrasing that reads fine ("I cannot see", "from my
  side"). Don't add typos or mistakes on purpose.
- Match the channel: Slack short and informal, PR comment direct, email
  fuller.
- Finish with the `pstack:unslop` pass. Its rules win over the samples only
  for AI tells, never for the writer's own phrasing.
`````
